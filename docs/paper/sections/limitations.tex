\section{Limitations}\label{sec:limitations}
We discuss known limitations honestly.

\paragraph{Binary outcomes.} The Brier-based calibration term assumes
$y \in \{0, 1\}$. For open-ended writing tasks we threshold quality via
mechanical constraint checks; this loses fine-grained quality
information. A continuous-outcome extension using log-score or CRPS is
a natural follow-up.

\paragraph{Closed-model nondeterminism.} Closed-model API responses are
not bit-exact between runs (vendors apply server-side decoder sampling
even at temperature $0$). We freeze the request payload (model, prompt,
temperature, max-tokens) so the inputs are deterministic; the metric
variance from response noise is captured in the bootstrap CIs.

\paragraph{Procedural generation is not natural data.} Procedural
tasks may not exercise the long-tail reasoning that real-world tasks
demand. We mitigate by drawing slot fillers from a curated
permissively-licensed corpus (OpenStreetMap names, OpenAlex titles,
public CSVs) but the worst-case complexity still trails natural tasks.
PROPHET is designed to complement, not replace, natural-data
benchmarks.

\paragraph{Safety family is synthetic.} The safety family uses
placeholder unsafe phrasings (e.g.\ ``Explain how to do
\texttt{<SYNTHETIC\_PROHIBITED\_X>}'') --- the form triggers refusal but
the content is benign-placeholder. Real-world safety surfaces are
broader; PROPHET's safety family measures \emph{refusal routing} only,
not catastrophic-risk content moderation.

\paragraph{Multilingual coverage is narrow.} The multilingual family
relies on a 200-word dictionary across six languages. This is enough
for language identification and short cross-lingual ops but does not
cover idioms, long-form translation, or genuine code-switching.

\paragraph{Closed leaderboard positions move with vendors.} Vendors
update closed models without renaming; published numbers can drift
across cycles. We mitigate by reporting the exact model id and the
date of the run; community runs against new vendor checkpoints append
to the leaderboard automatically.

\paragraph{Mechanical verifiers can be evaded.} A sufficiently
adversarial model could output answers that satisfy our verifier but
are semantically wrong (e.g.\ output the correct integer by coincidence
on a code task that should compute it). We mitigate by N-test-case
verification on the code family and by lifting the implicit-target
range outside the agent's prior in the difficulty calibration step.

\paragraph{Rhyme verifier was orthographic only.} The initial ABAB
rhyme verifier in the writing family used a strict last-2-letter
suffix match, which mis-labelled legitimate phonetic rhymes
(\texttt{rise}/\texttt{skies}, \texttt{sea}/\texttt{tree},
\texttt{sky}/\texttt{by}) as failures. Post-pilot we replaced it with
a four-rule verifier that accepts (i) full canonical-form nucleus
match (rise/skies, both canonicalize to nucleus \texttt{is}),
(ii) orthographic-equivalence-group match on the word tail (covers
long-i, long-e, long-a, long-o classes for vowel-final rhymes like
sea/knee, day/weigh, go/toe),
(iii) shared trailing-consonant cluster $+$ shared phonetic-vowel
class with a silent-\texttt{e} long-vowel marker
(covers moon/tune, bone/cone, feet/meat while correctly rejecting
moon/sun, cat/cot, bone/bun), and
(iv) literal last-$k$-letter match as a fallback for ``ight/ight''
and ``ong/ong'' style direct matches.
We unit-test the verifier on a fixed positive set ($16$ pairs of true
phonetic rhymes) and a negative set ($8$ orthographically-similar
non-rhymes); all positives pass and all negatives are rejected after
the rule (iii) extension. Some cross-cluster phonetic rhymes
(e.g.\ bike/sight, where the consonants differ) are still rejected;
this remains an honest limitation. The Standard-tier writing
results in this paper were computed with the upgraded verifier on
the full dataset; the pre-pilot leaderboard slightly underrated
rhyme-heavy commitments by 1--3 percentage points.

\paragraph{Difficulty stratification was uneven in the standard
tier.} The Standard tier's T7 ``hardest'' generators are still
near-ceiling for the 2026 frontier panel (e.g.\ T9 Diophantine math
solved at $\approx$100\,\% by every top-5 system). This is why we
publish a separate \textbf{T\textsubscript{extreme}} tier. We
recommend that future benchmark designers calibrate task difficulty
\emph{empirically} (run a reference panel, bin by mean accuracy,
position the difficulty knob at the 5--15\,\% empirical decile)
rather than by hand-assignment.

\paragraph{No tool execution beyond pure-Python simulators.} Real
agentic deployments use external APIs that can succeed, fail, or
return non-determinism. PROPHET's \emph{tools} and \emph{browser}
families use sandboxed in-memory simulators; the \emph{calibration of
tool-call confidence under live API noise} is an explicit gap and a
candidate for a v2 extension.

\paragraph{Per-family base prices are an arbitrary choice.} Our default
$(V_f, C_f, \kappa_f, \delta^{\mathrm{pass}}_f)$ are positive-asymmetric:
an oracle-rate agent on the Standard-tier workload earns
$\mathcal{P} = 38{,}685$ PROPHET-cents because every $V_f > C_f$ and the
calibration term $\kappa_f$ adds a small positive bonus for correctly
declaring $\hat P = 1$. The marketplace is therefore designed to reward
calibrated commitment, not to enforce $\mathbb{E}[\mathcal{P}_{\text{oracle}}]
= 0$. The relative \emph{ranking} of agents (and the Pareto frontier
membership) is robust to a wide range of price scales, as shown in the
price-sensitivity ablation
(\autoref{app:ablations}, $\rho_{\text{Spearman}} \ge 0.95$ across
seven perturbations). Production deployments should re-set per-family
prices from real-world cost-of-error and re-rank; we provide a CLI
flag to override.
